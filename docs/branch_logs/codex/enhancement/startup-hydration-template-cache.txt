Branch: codex/enhancement/startup-hydration-template-cache
Date: 2026-06-23

Why was the branch needed:
The app showed a jerky launch handoff on iOS while the first React screen and local data loaded, and the new-program template flow briefly rendered Loading templates before showing the empty state. The request was to move critical startup reads behind the launch handoff, keep the visible UI smooth, and avoid showing transient loading copy for template lists that can be warmed locally.

Outcomes of code changes:
The app now exposes an AppRuntimeCache through AppServices. Startup hydration blocks rendering on app state and the active workout view when an active program exists, then warms other persisted workout views for that active program in the background. When there is no active program, template summaries are preloaded while the user remains on the new-program start screen, and the Start action waits on the same cached promise before routing to Select Template. Template and workout mutation paths now refresh or invalidate relevant cache entries, reset clears the runtime cache for deterministic tests, and the web/native launch splash stays visible until hydration has completed.

Implementation decisions that were made:
The cache is app-layer, in-memory only, and dedupes in-flight app-state, template, and workout-view reads without adding schema changes, persistent storage, network calls, or dependencies. The workout repository gained a single program-scoped workout id query so background hydration can stay behind repository boundaries. Template invalidation cancels stale in-flight cache population so a mutation-triggered refresh cannot settle with pre-mutation data. UI updates use cache snapshots first and refresh through AppServices instead of importing application loaders directly where route state may already be hydrated.
