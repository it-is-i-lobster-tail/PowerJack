# PowerJack UI/UX Design Document

Version: 0.1  
Scope: Workout app styling, interaction design, mobile density, presentation, and subtle game-feel  
Platform direction: Rust/Dioxus, local-first, single-user, SQLite-backed app

---

## 1. Product Identity

PowerJack is a focused lifting app, not a broad health app.

The user opens the app, sees the active workout, logs sets, gets clear feedback, and moves on. The app should feel like a good barbell: simple, solid, reliable, and not desperate for attention.

The design should communicate:

- Energy without noise
- Structure without clutter
- Progress without dopamine casino nonsense
- Precision without looking like enterprise accounting software
- Speed without feeling twitchy
- Local-first simplicity without login ceremony

The emotional target is:

> “I opened the app, lifted, logged my sets, and it worked.”

That is the win.

---

## 2. Core UX Principles

### 2.1 Focus First

The gym is a high-focus environment. The UI should reduce decision fatigue and keep the user in the workout.

Rules:

- Show only what matters now.
- Hide future complexity until needed.
- Avoid dashboards during workout execution.
- Avoid decorative UI that competes with set logging.
- Do not make the user hunt for the active lift.

### 2.2 Mobile-First Density

Vertical space is limited. The workout screen must prioritize compact set logging.

The winning direction is the compact row/table layout:

- Exercise header at top
- Shared row labels: Set, Reps, Weight, Log
- Each set appears as a compact horizontal row
- Reps and weight sit on the same horizontal plane
- Logged rows show completion clearly but quietly
- Inputs remain large enough to tap accurately

This is the primary mobile workout logging pattern.

### 2.3 Hard Structure, Soft Actions

The app should use harder edges for structure and softer edges for actions.

Rules:

- Cards, sections, containers: 0–6px radius
- Buttons: 10–12px radius
- Inputs: 6–8px radius
- Modals: 8–10px radius
- Avoid pill-shaped everything

This keeps the product feeling focused and athletic, not bubbly.

### 2.4 State Should Be Obvious, Not Loud

The app needs strong status clarity without screaming.

Required states:

- Active
- Planned
- Complete
- Locked
- Halted
- Skipped
- Disabled
- Autosaved
- Error

State should be shown with a combination of:

- Color
- Border
- Icon
- Text label where needed
- Disabled affordance

Never rely on color alone.

### 2.5 Game Feel, But Invisible

The app should borrow the best part of games: fast feedback. It should not borrow the worst part: glittery manipulation.

The target is “felt, not noticed.”

Use subtle interaction polish:

- Fast tap response
- Slight button compression
- Immediate completion state
- Soft row highlight when a set completes
- Smooth expansion/collapse
- No confetti
- No XP meters
- No badges
- No fake achievement theater

## 3. Visual Design Language

### 3.1 Design Theme: Steel Focus

The chosen visual direction is dark, minimal, high-contrast, and gym-appropriate.

The app should feel like:

- Steel
- Chalk
- Rubber flooring
- Quiet focus
- Controlled effort

Not:

- Neon gaming UI
- Wellness spa app
- Medical tracker
- Social fitness feed
- Spreadsheet cosplay

### 3.2 Color Palette

| Role | Hex | Usage |
|---|---:|---|
| Background | `#0F1214` | Main app background |
| Surface | `#1C1F22` | Cards, panels, nav surfaces |
| Raised Surface | `#2A2E34` | Inputs, active blocks, selected containers |
| Primary Text | `#E6E9EC` | Main readable text |
| Muted Text | `#9CA3AF` | Secondary labels, metadata, placeholders |
| Border | `#374151` | Dividers, inactive outlines |
| Accent Green | `#22C55E` | Active, complete, success, selected |
| Warning Orange | `#F97316` | Destructive confirmation, caution |
| Info Blue | `#3B82F6` | Informational states only |
| Error Red | `#EF4444` | Validation errors and destructive failure |

### 3.3 Color Rules

- Green is the main action/status color.
- Orange is reserved for caution/destructive confirmation.
- Red is reserved for true error states.
- Blue is secondary and should be used sparingly.
- Do not use large saturated color blocks.
- Do not place long text on accent backgrounds unless contrast is verified.
- Prefer dark surfaces with colored borders/icons.

### 3.4 Contrast Requirements

Minimum goals:

- Normal text: at least 4.5:1 contrast
- Large text: at least 3:1 contrast
- UI components and meaningful icons: at least 3:1 contrast

The current palette supports strong contrast for primary text and muted text on the main background. Keep it that way. Humanity has suffered enough low-contrast gray-on-gray mobile apps.

## 4. Typography

Use system fonts for performance, platform fit, and simplicity.

Recommended scale:

| Element | Size | Weight |
|---|---:|---:|
| Screen title | 22–24px | 700 |
| Week / Day heading | 18–20px | 700 |
| Exercise name | 16–17px | 650–700 |
| Set row values | 15–16px | 500–600 |
| Labels | 12–13px | 500 |
| Helper text | 12px | 400–500 |

Rules:

- Use tabular numbers for reps and weight where possible.
- Keep labels short.
- Avoid decorative fonts.
- Avoid all-caps except tiny labels.
- Prioritize legibility while moving, tired, sweaty, and annoyed by gravity.

---

## 5. Spacing and Layout

### 5.1 Grid

Use an 8px spacing system.

Common values:

- 4px: tight internal spacing
- 8px: compact row spacing
- 12px: mobile card padding
- 16px: section spacing
- 24px: major screen separation

### 5.2 Mobile Frame

Mobile is the primary layout.

Rules:

- Use 12–16px page gutters.
- Avoid multi-column layouts on phones except compact set rows.
- Keep primary actions near the bottom when appropriate.
- Keep active workout context visible near the top.
- Make forms short and progressive.

### 5.3 Vertical Density

The app must save vertical space during workout logging.

Preferred pattern:

```text
Exercise Header
Set | Reps | Weight | Log
1   | [8]  | [185]  | ✓
2   | [8]  | [185]  | ○
3   | [8]  | [185]  | ○
```

Rules:

- Do not give every set a large card.
- Do not stack reps and weight vertically.
- Do not repeat labels inside every row.
- Use compact dividers instead of heavy boxes.

## 6. Component System

### 6.1 Buttons

Button types:

| Type | Usage |
|---|---|
| Primary | Continue, Next, Finish Workout |
| Secondary | Back, Cancel, No |
| Destructive | Yes, end current program |
| Disabled | Incomplete required selection |

Button rules:

- Minimum touch target: 44px height preferred.
- Border radius: 10–12px.
- Press state: slight scale or brightness shift.
- Disabled state: muted background, muted text, no shadow.
- Primary button should feel confident, not radioactive.

### 6.2 Inputs

Workout logging inputs:

- Reps and weight accept integers only.
- Values must be non-zero to complete a set.
- Empty state uses muted placeholder text.
- Backend-provided hints may appear as placeholder/hint values.
- Week 1 may show no weight hint.
- Reps may show a hint such as “2 RIR” where applicable.

Input behavior:

- Save automatically when both reps and weight are present.
- On save, transition row to complete state.
- If user edits a saved set, autosave again when valid.
- Invalid input should be blocked early on the frontend.

### 6.3 Cards and Sections

Cards should be crisp and restrained.

Rules:

- Use dark surfaces.
- Prefer 1px borders over shadows.
- Keep cards tight.
- Use shadows only for modals or elevated overlays.
- Do not nest cards inside cards unless absolutely necessary.

### 6.4 Modals

Use modals only for decisions that interrupt flow.

Example:

> End current program and start a new one?

Actions:

- No: return to current workout
- Yes: halt current program and redirect to new program setup

Modal rules:

- Centered on screen.
- Dim background overlay.
- Two clear action boxes/buttons.
- Destructive action uses warning orange or red treatment.
- Default safe action should be visually available.

## 7. Key Screens

### 7.1 App Startup

Goal: resume the user exactly where they left off.

Behavior:

- Load app state.
- If no active program exists, route to setup.
- If active program exists, route to active workout.
- Scroll/focus to active lift when possible.

UX rule:

> Never make the user manually navigate back to the lift they were already doing.

### 7.2 Program Setup

Setup should be progressive and low-noise.

Screens include:

- Program length in weeks
- Days per week
- Template/workout builder
- Exercise search/add flow
- Confirmation before replacing an active program

Rules:

- Next button is disabled until a valid selection exists.
- Selected option uses accent border and subtle filled state.
- No selection means no forward progress.
- Use concise helper copy.

### 7.3 Template Builder

Template builder requirements:

- Show workout days clearly.
- Add exercise button is visible but not overpowering.
- Search exercise interaction should feel quick.
- Added exercises appear in order.
- Exercise rows should show name and relevant muscle context when available.
- Keep edit controls minimal.

### 7.4 Workout Logging Screen

This is the core product screen.

Required layout:

- Week indicator above Day indicator
- Day navigation arrows
- Active workout content in one vertically scrollable page
- Exercise sections stacked vertically
- Compact horizontal set rows
- Finish Workout button appears only when all lifts are complete

Rules:

- If user is on Day 1, hide left arrow.
- If user is on the last day of the week, hide right arrow.
- Non-active workouts are readable but locked.
- Locked fields are greyed out and not editable.
- Completed workouts are locked.

### 7.5 Set Completion

A set is complete when:

- Actual reps exist
- Actual weight exists
- Both values are valid non-zero integers
- Save succeeds

Completion state:

- Show green check.
- Slightly brighten or outline the row.
- Do not animate aggressively.

### 7.6 Lift Completion

A lift is complete when all sets for that lift are complete.

Completion state:

- Exercise header shows completion mark.
- Section can remain expanded or collapse depending on flow.
- Keep completion obvious but quiet.

### 7.7 Workout Completion

A workout is complete when all lifts are complete.

Then and only then:

- Show Finish Workout button at bottom.
- On click, mark workout complete.
- Redirect/update user to next workout.
- If next workout is in next week, update current week.

Progression generation is handled elsewhere and should not clutter this UI spec.

## 8. Interaction and Motion

### 8.1 Motion Philosophy

Motion exists to communicate cause and effect.

It should never be decoration for decoration’s sake, because the phone is already a rectangle full of bad decisions.

Rules:

- Use motion to confirm input.
- Use motion to show hierarchy changes.
- Use motion to soften transitions.
- Avoid animations that delay logging.
- Avoid celebration effects.

### 8.2 Timing

Recommended durations:

| Interaction | Duration |
|---|---:|
| Button press feedback | 80–120ms |
| Input focus transition | 100–150ms |
| Row complete highlight | 150–200ms |
| Expand/collapse section | 150–220ms |
| Modal fade/scale | 150–220ms |

### 8.3 Game Feel Translation

Game feel concepts translated to this app:

| Game Concept | App Equivalent |
|---|---|
| Hit confirmation | Set saved/completed |
| Impact feel | Row check + subtle state change |
| Streamlining | Resume active lift automatically |
| Juicing | Minimal visual feedback, not spectacle |
| Clarity | Status visible without reading a manual |

The app should feel responsive because every action has a tiny, clear consequence.

---

## 9. Accessibility

Accessibility is not optional. It is part of making the app usable in a gym.

Rules:

- Prefer 44px touch targets for primary controls.
- Never rely on color alone.
- Maintain strong contrast.
- Support readable text sizes.
- Keep tap targets spaced enough to avoid accidental logging.
- Make disabled states visually distinct.
- Ensure form errors are explained in text.

Practical gym-specific accessibility:

- Assume one-handed use.
- Assume sweaty fingers.
- Assume poor lighting.
- Assume fatigue.
- Assume the user wants to finish the set, not admire the app.

## 10. Content and Copy

Voice:

- Direct
- Short
- Calm
- Useful

Good labels:

- Next
- Finish Workout
- Add Exercise
- Search Exercise
- End current program and start a new one?
- No
- Yes

Avoid:

- Motivational slogans
- Fitness influencer phrasing
- Over-explaining obvious UI
- Cute copy during serious actions
- Shame-based language

The app should sound like a spotter, not a LinkedIn wellness post.

## 12. Do / Do Not

### Do

- Optimize for fast set logging.
- Keep the active workout obvious.
- Use compact rows for sets.
- Use green for completion and active states.
- Use borders and subtle fill changes.
- Let the app resume exactly where the user left off.
- Keep destructive choices explicit.

### Do Not

- Do not build a generic health app.
- Do not require login for local use.
- Do not add social features.
- Do not use confetti, XP, streak badges, or loud gamification.
- Do not waste vertical space with one-card-per-set layouts.
- Do not bury workout flow behind menus.
- Do not rely on color alone for state.
- Do not make the user think about database state.

---

## 13. Acceptance Checklist

A design pass is acceptable when:

- The app looks consistent across setup, builder, and workout logging.
- The workout logging screen uses compact horizontal set rows.
- Reps and weight are visible on the same row.
- Disabled buttons are clearly disabled.
- Selected options are obvious.
- The Finish Workout button only appears when valid.
- Locked workouts/lifts/sets are readable but not editable.
- Primary controls meet mobile touch target expectations.
- Text contrast meets accessibility targets.
- Motion feels immediate but not flashy.
- The app feels calm, fast, and purpose-built for lifting.
